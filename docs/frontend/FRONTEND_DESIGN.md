# Frontend Design

- Status: Playable gray-box boundary implemented; Coal-Twilight visual direction adopted

## 0. Decision Summary

바닥이 사라지는 술래잡기 uses one static browser application. PixiJS 8 with WebGL owns the game world. Semantic HTML, DOM, and CSS own setup, settings, results, fatal errors, focus, and accessibility text. TypeScript 7, Vite 8, Bun, Oxlint, and Oxfmt form the accepted toolchain baseline.

React, Vue, Svelte, Phaser, Tailwind CSS, a general state manager, and a general-purpose physics engine are not part of the initial baseline. The contest-submission visual direction is Coal-Twilight: a single dark palette shared by the DOM shell and the PixiJS canvas. Character, item, terrain, pirate-ship, cannonball, boulder, explosion, seawater-impact, and eight active skill-effect sprites have passed the asset ledger and now layer over the procedural renderer. The retired Stone Prison source sprite is not loaded. The rejected opaque-checkerboard sheets stay outside the runtime. Procedural action geometry remains authoritative because its direction and timing must stay readable above character art and remains the optional-asset failure fallback. Reduced-motion presentation preserves the same telegraph timing with fixed scale and rotation.

## 1. Product Surface and Scope

The primary surface is a short desktop-or-mobile browser single-player game reached through a public HTTPS link. The default entry point must reach quick start without installation, account creation, or a network service. Online multiplayer, authentication, a backend, a database, runtime LLM calls, and remote analytics are outside the MVP.

## 2. User Flow Map

The minimum user flow is load, menu, complete setup, game start, a pausable `3→2→1` countdown, play, elimination or victory, and immediate restart through a fresh countdown. The first visit has no selected attributes, skills, or item. `게임 시작` opens a modal explanation until the player saves exactly 20 attribute points, two skills, and one item; its primary action opens settings. Settings edits remain draft values until `설정 저장`, then return to the menu, and later starts consume the last saved in-memory values. Version history is another static secondary branch: it renders concise newest-first milestones, returns through `메뉴로` or `Escape`, and restores focus to its launcher without creating URL or persisted state. Required initialization failure disables start and enters a recoverable DOM error state. There are no application permission or authentication flows.

## 3. Routing Contract

The MVP is a single-page static application with one document route. URL parameters, query-driven game state, hash routing, redirects, and shareable configuration are not part of the initial contract. Static hosting must support both root and configured base-path builds without application routing.

## 4. Page and Layout Model

The DOM shell owns the initial menu, version history, settings, HUD overlays outside the game world, results, errors, and accessibility text. After start, the arena becomes a fixed full-viewport surface with no document scrolling; match information and round controls live either as translucent map overlays or inside the P pause layer instead of consuming layout below the canvas. Completed-round and fatal variants reuse that panel but never expose the resumable `계속` action; restart, menu, report, and sound controls remain available. The PixiJS canvas is hidden before play and owns arena tiles, participants, items, pirate ships, the gold-and-teal treasure ship, gift deliveries, cannon and rock trajectories, impact effects, and a human-follow camera after start. The camera renders a local viewport and clamps at the projected world edge with an ocean margin large enough to reveal offshore attackers and the treasure ship; it never shrinks the full island into one screen. Presentation uses a fixed 58-degree elevation: world depth is foreshortened by `sin(58°)`, while simulation and collision coordinates remain top-down.

## 5. State Ownership Model

The pure simulation owns round state. The application layer owns the fixed-step accumulator, countdown elapsed time, screen and round lifecycle, generated local seed, pause reasons, manual kill-reward trait delivery, and the applied human-upgrade history used by the local report. The DOM shell owns the initially empty six-attribute draft, two-skill and one-item drafts, setup completeness, the setup-required dialog, the six-choice kill-reward dialog, last-saved in-memory settings, focus, match-readable status, restart, and menu return. PixiJS owns presentation objects derived from read-only state. There is no server state or durable URL state. Presentation layers cannot mutate simulation entities directly.

## 6. Data Fetching and Cache Policy

Application data fetching and cache invalidation are `NOT_APPLICABLE`. Required static assets load from the same origin. Optional character, item, terrain, and skill-effect images start loading without blocking countdown or simulation; missing files retain their procedural fallback and the renderer reports a partial asset state. Optional audio failure falls back to silence. A required renderer or content-contract failure blocks round start with a recoverable error screen.

## 7. Component Boundary Model

The application composes simulation, AI, presentation, platform adapters, and content. Simulation remains pure TypeScript and cannot import PixiJS, DOM, browser clocks, or ambient randomness. AI emits the same participant command shape as human input. PixiJS and DOM consume read-only state and events. Generic `shared`, `utils`, and framework-shaped layer hierarchies are not created without a concrete owner.

## 8. Design Token Contract

Semantic tokens must distinguish canvas background, stable tile, warning tile, void, human participant, bot participants, focus, cooldown readiness, mass state, success, danger, and disabled controls. The Coal-Twilight palette is the adopted contest-submission direction and is shared between the DOM shell (`src/styles.css`) and the PixiJS canvas (`src/presentation/arena-renderer.ts`):

- Void surface: `#0c0f0e` (page), `#141816` (canvas and arena host)
- Tile surface: generated grass and coast art keeps its natural color through every pre-impact phase; warning marker `#ffc857`; critical skull marker `#ff5c4d`
- Human identity: `#3b8cff` focus accent, doubled as a guard ring plus diamond body stroke so the human is identifiable among 50 participants
- Action telegraph: ShoveWindup amber `#ffc857`, ShoveActive red `#ff695c`, DodgeActive cyan `#68d8d6`, Stumbling magenta `#d58bea`
- Mass ring scales stroke width with `massFactor`; iron-boots badge and feather chevron provide non-color mass signals
- Success `#5fd6a6`, danger `#ff5c4d`, warning `#ffc857`, warm accent `#ff8f5c` for Mayhem mode

Color is never the only signal for collapse warning, player identity, or action readiness. Collapse uses shape (diagonal cross, X-hatch), identity uses shape (diamond) plus a doubled ring, and action readiness uses direction-line width and color together.

The 2.5D depth contract keeps tile tops rectangular and only exposes a dark 6–14 CSS-pixel cliff front where a supported tile has no southern neighbor. Generated coast frames retain grass, sand, and foam but remove their embedded blue water at load time; those transparent pixels reveal one viewport-wide ocean surface, preventing neighboring shore tiles from stitching unrelated water patterns into visible crosses. Stable generated terrain does not retain a procedural opaque rectangle beneath that cutout. If image access or canvas processing fails, the original opaque frame remains the bounded asset fallback; if the terrain atlas fails, the full procedural tile renderer remains the independent fallback. Character frames preserve transparent headroom; bottom-row variants compensate for the larger crop at display time so hats and round heads remain intact without making those four bodies visibly smaller. Characters and items remain upright instead of being vertically squashed, receive bounded elliptical ground shadows, and are drawn by interpolated world Y so nearer participants cover farther ones. Facing lines and world effects use the same projected vector plane. Eight active 512×512 alpha PNGs provide distinct cast and hit silhouettes for every reusable skill. Directional effects rotate from the projected simulation vector. Meteor Mark and Frost Field retain bounded sprites on their authoritative zones, while Aegis follows a shielded participant until shield health is gone. The 25-plus-participant mode retains the fourteen-transient-effect cap, and sprite maps reuse instances by event, zone, or actor key instead of allocating replacements every frame. Missing skill art leaves the procedural geometry visible and cannot block simulation or round start. The projection is presentation-only and cannot change support, collision, AI, replay hashes, or deterministic outcomes.

## 9. Interaction and Accessibility Contract

The input contract accepts arrow-key movement, mouse or touch drag anywhere in the arena, a mobile virtual joystick, and a standard gamepad left stick or D-pad. `Q/W`, the first two gamepad face buttons, and two touch buttons activate the selected reusable skills. `E` activates the shared cooldown-based Grappling Hook and does not occupy a loadout slot. `D`, the first gamepad shoulder button, and one touch button activate the single inventory slot. The desktop in-round action HUD keeps those four controls in one fixed `Q→W→E→D` vertical column; state or label changes cannot wrap them into multiple columns. `P` toggles a manual pause layer that owns live round statistics, controls, sound, restart, report, and menu actions; `Escape` or `계속` resumes it. Shift has no gameplay meaning. Manual pause remains authoritative across blur/focus and renderer restoration. `WASD` and `Space` have no gameplay meaning. Every adapter writes the same bounded human command state sampled once per fixed tick; simultaneous skill or item edges choose the lower slot, pointer input overrides gamepad input while actively dragged, gamepad input overrides held arrow movement while displaced, and releasing or losing focus restores a neutral vector and stops ordinary locomotion immediately. Setup offers six keyboard-native `0..20` steppers that must allocate exactly 20 points, exactly two unique combat skills from eight, and exactly one charged item from five. The six trait cards form a two-column, three-row grid at desktop width and collapse to one column on narrow screens. A separate four-column, three-row summary exposes twelve derived combat values, including health and mana regeneration. Remaining points are announced live and save is disabled until allocation is complete. Settings do not repeat the complete build in a second summary banner. Skill and item cards separate compact cost, cooldown, charge, and targeting metadata from the concrete effect description. The starting item occupies `D`; map pickups replace the depleted slot and cannot be collected while it retains charges. The in-round overlays expose health, mana, nearby combat bars, selected-skill and Grappling Hook cooldowns, mana affordability, item charges, control states, and effective stat bonuses. The pause layer accumulates actual human path distance, health damage dealt and received, shield absorption plus its share of attempted damage, active slowed ticks, and selected-skill use counts from authoritative step frames and events. A credited elimination pauses simulation and opens six keyboard-native radio choices: Pressure, Stability, Mobility, Reflex, Vitality, and Focus. Every uncapped trait is immediately available; there are no prerequisite paths or skill-rank rewards. The selected card exposes current rank and the per-point effect, the dialog owns bounded internal scrolling on short screens, and its save action remains reachable. Saving queues one stat command and resumes only when visibility and renderer state also permit it. Completed, inactive, Falling, or Eliminated human state wins over the dialog and cannot accept a choice. `Q/W/E/D` enter a shared visible aiming state for directional and ground actions. While aiming, arrow keys move the target instead of the participant; the same action key or `Enter` confirms, `Escape` cancels, pointer hover updates the same target, left-click confirms, and right-click cancels. Confirmed out-of-range ground actions approach until valid, while a new movement input cancels that approach and becomes ordinary movement. Self-target actions bypass aiming and execute on the next simulation command. Gameplay action keys are ignored when an input, link, or button owns focus. Window blur and document visibility loss clear held input and pause the scheduler. The complete app shell disables text selection and native image dragging while preserving buttons, tabs, steppers, ranges, and keyboard focus behavior.

The Grappling Hook row shows its 15-second base reuse time while ready, switches to the live one-decimal remaining cooldown after use, and mirrors blocked or cooldown state on the compact touch action.

The experimental tuning lab exists only in development builds and is absent from the production DOM. It starts collapsed and disabled, then exposes bounded sliders for base movement speed, light/heavy speed multipliers, hand reach, active ticks, dodge speed, and dodge ticks when enabled. Ordinary movement acceleration is intentionally not tunable because locomotion is direct. Values apply to the next round for both human and bots, can be reset, and copy as local schema `shovefall-debug-tuning/v1`; they never persist or upload.

Settings navigation is a four-card ARIA tab list: Attributes, Skills, Items, and Lab. Only one tab panel is rendered at a time; arrow keys, Home, and End move between available tabs. Attributes is always the entry panel and shows current derived weight adjustment, health, mana, movement, cooldown, outgoing force, knockback resistance, and control duration alongside each attribute's exact next-point delta. The internal mass multiplier never appears as a player-facing unit: neutral reads `기본`, and Strength investment reads as a percentage above that baseline. Lab and its tab exist only in development builds.

Each starting-attribute card uses one compact vertical stepper ordered as increase, current value, and decrease. The controls retain explicit per-attribute accessible names and disabled states at the remaining-budget boundary. Starting-skill and starting-item cards keep full-card native input ownership while hiding the redundant checkbox or radio glyph; selection is communicated by the card's blue border, and keyboard focus retains its own visible outline. Skill cards add one decorative repository-owned icon in the same 64-pixel visual slot as item art and two separate text lines: mana plus cooldown first, then the concrete range, damage, knockback, control, radius, delay, or duration that applies. Text remains the complete contract when decorative art is unavailable.

## 10. Loading, Empty, Error, and Disabled States

Boot has loading, ready, unsupported-renderer, required-content-error, and retry states. Setup disables start only when normalized configuration cannot be produced. Playing exposes paused and fatal-invariant states. Optional media failure does not create an empty game state.

## 11. Form and Validation Model

Settings are local client inputs validated at the DOM boundary and normalized again by the application contract. There is no backend validation. Invalid user-controlled values are constrained with visible feedback; invalid project-owned content blocks start rather than silently inventing defaults.

## 12. Responsive and Layout Rules

The layout supports narrow mobile viewports without covering setup controls. A coarse pointer or viewport at or below 820 px reveals an arena-overlay virtual joystick and four skill/Hook/item buttons; touch may also drag anywhere outside those buttons. Once a round starts, both desktop and mobile arenas use the full dynamic viewport, honor safe-area insets for overlays, and remove page scrolling instead of stacking controls below the canvas. The pause and six-choice trait panels own bounded internal scrolling on short screens. DOM controls remain at least 44 CSS pixels, and device-pixel ratio stays capped by measured performance policy. Physical-device and safe-area testing remain release evidence gates rather than inferred support claims.

## 13. Observability and Analytics

Remote analytics, session replay, advertising, and automatic error upload are excluded. The normal HUD contains only match-readable state. DEV bootstrap creates one collapsed `data-development-only` panel for tick, rate, position, seed, and state hash; production HTML contains no panel markup and production never creates or updates those outputs. Fatal errors may show copyable non-secret reproduction metadata without uploading it. Completed rounds may copy a local versioned playtest record with seed, normalized settings, result, and state hash; this is a user-triggered clipboard write, not analytics. Separately, the scoreboard persists only a bounded non-secret summary of the latest fifty completed rounds in this browser and never uploads it.
